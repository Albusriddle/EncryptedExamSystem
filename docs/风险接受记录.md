# 风险接受记录

- 记录日期：2026-10-29（首次决策）；本版随 **v1.9.1** 复核，事实未变
- 适用版本：v1.0.0 及后续 1.x
- 决策：**项目接受下列已识别的安全风险，不实现 P0 的 per-student / Header 签名格式（容器 v9），
  也不升级答题卡到能证明作者身份的格式。**

> 本记录**不是**「风险已修复」的声明。它说明项目为什么在已知残余风险下继续使用当前格式，
> 以及使用时必须遵守的补偿措施。任何「读不到题目」「防伪造答题卡」的绝对承诺都不成立。
>
> 事实依据见 [安全边界与威胁模型](安全边界与威胁模型.md)；实现层面的取证见
> [代码审阅报告](代码审阅报告.md) 的「当前基线」与相关轮次；时间线见 [发布说明](release-notes.md)。

## 0. 怎么读这份记录

每条风险固定五段，缺一段就说明这条风险还没被真正评估：

| 段 | 回答的问题 |
|---|---|
| **事实** | 代码 / 格式现在究竟允许什么（可对照实现核对） |
| **影响** | 被利用后损失到什么范围 |
| **接受理由** | 为什么在当前版本不修（成本、格式代价、定位） |
| **补偿措施** | 使用现场必须做什么来降低概率与损失 |
| **复审条件** | 出现什么情况必须重新评估（可量化、可触发） |

四条读法（决定了后面每一条的分量）：

- **「接受」是决策，不是缺陷待办**：写进本记录的事项不会因为「还没修」而被当成 bug 排期；
- **接受不是修复**：本记录中的每一条都仍然成立；把 R-01 ~ R-06 写成「已解决」「已修复」是错误陈述。
  `风险接受` 与 `缺陷修复` 是两条不同的轨道：本文件只处理前者，后者见 §8；
- **补偿措施是流程，不是技术修复**：现场监考、现场收卡、名单保密、启用 PIN 都属于流程约束，
  可以被绕过，也不改变「软件本身允许什么」；
- **引用本记录不能豁免工程质量问题**：见 §8，那些仍必须修。

## 1. 接受的风险（总览）

先看总览，再看 §2 起的逐条细节。

| 编号 | 一句话 | 泄露 / 绕过的东西 | 主要补偿 |
|---|---|---|---|
| R-01 | 同场题干可被本场学生解出 | 题干（答案 / 判分材料已剥离） | 现场监考 + 按场次拆库 |
| R-02 | 他人答题卡可读 / 可伪造 | 作答内容、作者身份 | 现场收卡 + 必须带 `--package` 校验 + 收据 |
| R-03 | 无 PIN 时学号即身份 | 该生信封与本场题干 | 高风险启用 6 位 PIN |
| R-04 | Header 可重加密 | 时间窗、回看策略 | UI 约束 + 统一开考收卷 |
| R-05 | 网页模式挡不住中间人与浏览器 | 传输之外的一切 | 自签 TLS + 指纹核对 + 隔离局域网 |
| R-06 | 明文下监考令牌可被嗅探 | 收卷 / 终止的写权限 | 默认 HTTPS + `tls-only` 逃生阀 |

## 2. R-01 同场学生可解出本场全部题干

**事实**：每个场次只有一个 `session_secret`，`PayloadData.banks` 保存本场完整题库。
学生用自己的学号（+ 可选 PIN）解开信封即得到 `session_secret`，可解出本场**所有**题干；
`answer` 与 `judge` 在打包时已剥离。密码学形状是：

```text
envelope_j = AEAD( Argon2id(学号_j ‖ session_id ‖ salt [‖ PIN]),  student_id ‖ S_j ‖ exams ‖ sections )
data_i     = AEAD( HKDF(S_i, "bank"),  { banks, picks, bank_index, ranges } )
```

包里**不含任何学号明文**（单测 `student_ids_never_appear_in_payload` 覆盖十进制 ASCII / LE / BE
三种形式），但这不改变「本场学生共用一个 `S_i`」这一事实。

顺带把 `samples` 的边界也钉在这里：v1.9.0 起题目级的 `samples`（输入 / 输出示例）会**留在包里**——
它是**给学生看的**演示数据，不属于答案材料；大题 `answer.samples` 嵌在 `answer` 里，随 `answer`
一起被剥离。因此 `samples` 留在包里不扩大 R-01 的范围，也不构成新的泄露面。

**影响**：本场题干可被合法名单内学生获取并扩散；不能读其他场次，不能读标准答案。
同场学生仍可把题干抄走 / 拍照外传；`session_secret` 一旦泄漏，本场全部题干都可被离线解开。

**接受理由**：

- 系统定位是「防误操作 + 现场监考」，不是防逆向的强保密系统；
- 题干泄露的损失低于标准答案泄露，且现有流程依赖现场监考；
- 真正修复需要 per-student 试卷数据与密钥，属于 P0 新格式（v9；v8 已被代码题门禁占用），
  当前版本不做。

**补偿措施**：

- 重要考试必须现场监考、禁止携带可运行程序的设备；
- 题库按场次拆分，减少单场题干暴露面；
- 不把「题干绝对不可见」作为对教师的承诺。

**复审条件**：考试改为远程 / 无人监考；题干进入合规审计范围；发生本场题干扩散事件；
或需要把「题干保密」写进合同承诺。

## 3. R-02 同场学生可读取 / 伪造他人答题卡

**事实**：答题卡密钥 = `HKDF(K_manifest, salt = hex(paper_fingerprint), info = "ees-answer-sheet-v1")`。
`K_manifest` 在包内以掩码形式存在、可被提取，所以同场学生能解开、修改、重新加密他人的 `.eea`。
`check_binding` 只用包内数据重算该生试卷，比较**试卷指纹与题目列表（qids）**，
**不证明答题卡的作者身份**。收据是可选审计措施，不是必经流程。

答题卡本身的形状（`EESANS02` / v2）：

```text
MAGIC(8) | version(4) | student_id(8) | session_id(4) | paper_fingerprint(64 个 hex 字符) | AES-256-GCM 密文
AAD = student_id ‖ session_id ‖ paper_fingerprint     // 换人 / 换场 / 换卷都会解不开
上限：单题 1 MiB、整卡 16 MiB（MAX_TOTAL_ANSWER_BYTES）
```

AAD 只绑定「声称的学号、哪一场、哪份卷」，而密钥材料（`K_manifest` + 试卷指纹）都能由
**本场任何一个能解锁题库的学生**算出来——所以他能为同场任何人造出一张「格式与绑定都正确」的卡。
这正是 R-02 的来源。

**影响**：同场学生可读取、修改或伪造他人 `.eea`；教师端绑定校验只能发现「不是本包原卷」，
不能发现「不是本人填写」。学生之间互相拷贝答题卡无法被工具发现；收据只在「收卷之后」这条
时间线上有意义。

**接受理由**：

- 现有收卷流程是现场收卡 / 统一拷贝，答题卡不经学生自提交；
- 真正修复需要 per-student 答题卡密钥或教师侧签名链，属于新格式，当前版本不做；
- 收据可检测收卷后的改动，但不能替代身份认证。

**补偿措施**：

- 收卷必须现场完成，学生不得自行提交 / 转发 `.eea`；
- 教师校验时**必须**选择学生端包（`verify-answer-sheet --package` 强制要求），
  不接受「未做绑定校验」的通过状态；
- 重要考试启用答题卡收据，并核对**签发人指纹**（16 位）；
- 不把 `check_binding` 当作「作者身份认证」。

**复审条件**：答题卡改为学生自行上传 / 邮件提交；需要区分「谁填的」而不只是「哪份卷」；
发生伪造答题卡事件；或成绩争议需要可举证的作者身份。

## 4. R-03 默认无 PIN 时，任意已知名单内学号可解锁

**事实**：`--pin-login` 默认关闭；无 PIN 时入场密钥只依赖
`Argon2id(学号 ‖ 场次 ‖ salt)`。知道名单内任意学号的人可以解锁该生信封。启用后 PIN 为 6 位数字，
输入 1–5 位会自动左补 0；PIN 表用 `HKDF(master, salt = 包 salt, info = "student-pins")` 加密，
学生端即使拿到 `K_manifest` 也读不到 PIN 表（那是 master 另派生的密钥）。

**影响**：可冒用同场学生身份获取该场题干；与 R-01 叠加后影响扩大。
另外**「启用 PIN」这件事的强度也得按实际情况说**：6 位 PIN 的搜索空间只有 **10⁶**，按既有实测
约 **92 ms/次** 的 Argon2id 派生（64 MiB / t=3 / p=1，2026-10-22 记录）推算，单机多线程穷举是
**「小时级」而不是「年级」**；离线学生端也没有在线限速这一层。所以 **PIN 抬高的是成本，
不是密码学边界**，仍需现场监考兜底——这一点比「必须启用 PIN」更重要。

**接受理由**：

- 默认零配置是产品可用性要求；
- 低风险 / 随堂场景由现场监考与名单管理控制；
- 高风险场景可显式启用 `--pin-login`，**无需改变容器格式**。

**补偿措施**：

- 高风险考试必须启用每生 6 位 PIN；
- 名单与 PIN 表按考试保密要求管理，不公开传播；
- 发现异常登录时按场次作废 / 重考处理。

**复审条件**：出现冒名登录事件；名单大范围外泄；或考试要求「仅本人可解锁」而现场无法核对身份。

## 5. R-04 Header 可被重加密，时间窗 / 回看策略可被改包绕过

**事实**：Header（场次起止时间、`time` 令牌配置、`student_review`、`pins_ct`、`salt`、`kdf`）
只由包内 `K_manifest` 加密，**没有签名**。学生可还原密钥、修改 Header 后重新加密。

**影响**：时间门禁、到点自动收卷、学生回看策略只对「不改包」的学生有效，不能作为密码学边界。
改包的学生可以「提前开考」或「延迟收卷」；教师端看到的是收上来的答题卡，看不到学生的运行环境。

**接受理由**：

- 纯客户端无法防拥有本机完全控制权的学生；
- Header 签名需要教师密钥与 P0 新格式（v9），当前版本不做；
- 现场监考与网络时间仍是主要控制手段。

**补偿措施**：

- 时间门禁按「UI 约束 + 现场监考」宣传，不作为防绕过保证；
- 重要考试使用现场统一开考 / 收卷，不依赖学生端自动冻结；
- 不把 `student_review` 当作强制保密控制。

**复审条件**：考试时间窗成为成绩有效性的唯一依据；需要向第三方证明「学生不能延长时间」；
发生改包延长时间的事件。

## 6. R-05 网页考试模式：传输加密的边界与浏览器不可控

**事实**：v1.4.0 起可选「本地 `exam-server` + 学生浏览器」（**「可正常作答」自 v1.4.2 起**：
v1.4.1 修 `body` 不渲染、v1.4.2 修填空 / 改错编码）。按约定只用于**隔离局域网 + 现场监考**。
v1.5.0 起**默认 HTTPS（自签证书，首次启动自动生成）**；明文端口（默认 8080）只回 301 跳转、
不承载任何页面或数据；只有显式 `--tls off` 才回到明文 HTTP。
服务端只持有考试包与 `K_manifest`，**不持有 master 与标准答案**。

**影响**：

- 自签 TLS 能挡住同网段的**被动嗅探**（抓到的只是密文）；
- **不挡主动中间人**：除非学生把浏览器里看到的证书指纹与教师屏幕核对一致——自签没有公共 CA 背书；
- **不防主机木马与浏览器扩展**：它们本来就能读页面内存与设备上的密钥，网页应用无解；
- 浏览器无法阻止 DevTools、切屏、截图、搜索；
- 教师机是单点：断电 / 休眠 / 崩溃会影响全场。

**接受理由**：

- 网页模式解决的是「机房没有可运行 exe 的环境 / 设备不统一」，不是提高安全等级；
- 传输层默认加密、明文端口不承载数据，已把「同网段被动嗅探」这一档降到可接受；
- 主动中间人需要教师现场核对指纹，属于流程补偿，不属于软件能单独解决的问题；
- 真正修复（客户端证书绑定、端到端加密页面内容）会引入设备管理成本，超出校内考试范围。

**补偿措施**：自签 TLS（v1.5.0 起默认开）、启动横幅打印证书指纹供核对、外部证书启动自检
（私钥 / EKU / 链 / 有效期 / SAN，v1.6.0 起）、明文端口只做 301 跳转、专用 AP、关闭客户端隔离、
现场监考、UPS、作答实时落盘、事件日志。v1.4.3 起额外两项：服务端启动时三源校时（默认只告警，
可配置为不通过拒绝启动）、作答状态文件与事件日志只授予当前系统账户（Windows 受保护 DACL /
Unix 0600）。v1.4.5 起「答案实时落盘」才真正成立：每次保存都写加密状态，崩溃后重登可恢复未交卷
作答。不使用网页模式时，这一整条风险不成立。

**复审条件**：网页模式用于非隔离网络或远程考试；学生设备无法核对证书指纹；教师机不再由
考务人员控制；或需要把「传输不可窃听」写进合规结论。

## 7. R-06 监考页在明文模式下允许写操作

**事实**：v1.8.0 起服务端提供监考页（`/monitor`）与写接口（收卷 / 终止 / 批量收卷 / 解除）。
默认 `--monitor-write-mode allow`：即使 `--tls off`（明文），写操作也允许，因为部分机房只跑
明文排障。

**影响**：明文下监考令牌可被同网段嗅探；拿到令牌的人可以替学生收卷、终止其作答（可解除），
甚至批量收卷。令牌本身是高熵随机值（32 字节 hex ＝ 64 hex 字符）、只存在教师机
（`<答题卡目录>/monitor.token`，0600 / 受保护 DACL），不落 cookie、不落日志（审计只记
SHA-256 前 8 位），泄漏面主要是「地址栏 / 屏幕被拍照」与「明文嗅探」。

**接受理由**：

1. 不做监考页的代价更高：老师只能靠翻日志与答题卡目录判断进度，收卷还得逐台机器催；
2. 明文本来就是「同网段可嗅探」的部署（同一条 R-05 已接受题干 / 作答可被嗅探），
   多一个可被嗅探的令牌不改变这一档位的信任假设；
3. 提供逃生阀：`--monitor-write-mode tls-only` 让明文写操作直接 403；
4. 误操作可回退到「可登录」：终止可「解除」；但**封存不撤销**——学生重登看到的是「已交卷」，
   若要他继续作答只能新建场次 / 重发试卷。答题卡在终止时已封存，不会丢。

**补偿措施**：

- 默认 HTTPS；明文只在排障时使用，启动横幅会红字警告；
- 令牌文件 0600 / 受保护 DACL，重启复用（书签长期有效）；**删掉 `monitor.token` 重启会重新生成，
  旧书签随之失效**，需要重新从启动横幅取地址；弱令牌默认拒绝启动；
- 写操作要求 `POST` + `X-Monitor-Token` + `X-EES-CSRF: 1`，全部写进 `events.jsonl` 审计；
- 批量收卷必须带 `{"confirm":"收卷"}`，服务端再校验一次；
- 写操作有 **1 秒冷却（429）**，防止脚本把教师机磁盘打成瓶颈；
- 正式考试建议用默认 HTTPS；考完删掉 `monitor.token`。

**复审条件**：明文成为常态部署；令牌泄漏或出现未授权收卷 / 终止；监考页暴露给学生网段；
或需要把监考操作作为处分依据（此时需要更强的操作者身份认证，而不只是共享令牌）。

## 8. 不在本记录中接受的事项

下列问题**不是**安全边界，仍需按普通缺陷修复，不能引用本记录豁免：

- 重叠场次导致学生被路由到错误场次（v1.0.2 起改为按信封 tag 过滤 + 时间窗内回退）；
- Verify / Keygen 子进程残留、答题卡 `recovered` 文件恢复、测试门禁误判等工程质量问题；
- 任何会导致正常考试无法进行、答题卡丢失或成绩错误的功能缺陷；
- 答题卡格式 / 容器版本不兼容导致的收卷失败（应通过同步升级解决，不是「接受风险」）；
- 网页端「保存失败却显示已保存」这类状态谎报（属于可用性与可信度缺陷）；
- 监考页、网页作答的任何越权（学生 cookie 调监考接口、GET 调写接口等）——这些是缺陷，
  v1.8.1 已补用例守着。

## 9. 复审触发条件（全局）

出现以下任一情况时，必须重新评估本记录，并优先实施 P0 新格式（v9）：

1. 考试要求从「现场监考」变为「远程 / 无人监考」；
2. 题干或答题卡进入合规审计范围；
3. 发生同场题干扩散、答题卡伪造或时间窗绕过事件；
4. 需要把「防伪造 / 防篡改」作为对客户的合同承诺；
5. 网页模式成为主要交付形态，或监考页从「辅助」变成「处分依据」；
6. 本记录引用的实现发生变化（容器版本、答题卡版本、时间令牌模式、监考写模式），
   导致上述「事实」段不再准确。

复审结论只有两种：**维持接受**（写明复核日期与依据）或**启动 v9**。
不存在「先不写记录、先上线」这个选项。
