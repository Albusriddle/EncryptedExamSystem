# 保密考试系统 —— 架构与实施方案

> 目标：管理端（教师/教务处）编排多场考试 → 打包加密题库 → 生成"学生端"自解压包 → 学生凭学号 + 网络时间门禁解锁 → 离线抽题生成个人试卷。

---

## 0. 先说结论：需求里的三个硬矛盾

这个项目的功能描述本身是自洽的，但**"保密"这个词和下面三点存在结构性冲突**。方案必须先解决它们，否则做出来"能跑但一攻就破"。

### 矛盾 1：自解压包（SFX）的密码不可能真正"只嵌在外部壳里"

SFX = `自解压 stub（exe） + 压缩数据`。stub 运行时必须拿到密码才能解压，所以：

- 如果密码编译进 stub，用 7z 解包 + 反汇编 / 字符串搜索 / `frida` 挂钩 `CryptDecrypt`，10 分钟内就能拿到 64 位 hex 串；
- 更致命的是：**多个学生的密码是同一个**（管理端只设置一个 64 位 hex）。任何一个人拿到密码，把解压出来的 exe + 题库转发给别人，全班就都拿到了。

**对策（必须做）**：密码不写进 stub 的明文常量，而是由 stub 在运行时**现场拼装**：
用白盒表 / 分片混淆存 32 个 nibble（每个 nibble 与学号、场次编号做一次可逆变换），运行时用 `学号 + 场次号` 现场还原。
这样即使静态逆向，也需要理解拼装逻辑；同时**每场考试一个独立密码**（不同场次不同密钥），泄漏面从"全班"缩到"某一场"。

> 真要做强：stub 里只存**密钥分片**，完整密钥由"网络时间服务器返回的一段数据"参与派生（见 §3.4）。离线拷贝 = 解不开。

### 矛盾 2："网络时间做门禁"是最薄弱的一环

时间门禁的本质是：**客户端永远可以被改时间**。但我们可以把攻击成本从"改系统时间 3 秒"抬高到"要能伪造一个 TLS 会话"：

| 级别 | 做法 | 攻击成本 |
|---|---|---|
| L0 | 读本机系统时间 | 改一下系统时间，0 成本 |
| L1 | HTTP 请求 `Date` 响应头 | 改 hosts / 中间人 / 断网重放，低 |
| L2 | **TLS 握手时读取证书 `notBefore/notAfter` 与服务器 `Date` 头，并强制校验证书链** | 需要伪造证书链，中 |
| L3 | L2 + 服务端下发**签名时间令牌**（`timestamp + nonce` 用 Ed25519 签名，客户端内置公钥验签） | 需要私钥，高 |
| L4 | L3 + 令牌里绑定 `学号 + 场次 + 包指纹`，且**服务端记录一次性 nonce**（防重放） | 需要私钥 + 在线，最高 |

**推荐 L3**（不引入服务端状态，成本可控），需要防重放再加 L4。

关键实现点：**不要只信一个时间源**。并行请求 3 个独立源（自建 NTP/HTTPS 时间服务 + 阿里云/腾讯云 NTP + 国家授时中心），取中位数；若三源偏差 > 5 分钟则拒绝解锁并提示"网络异常"。这能挡住绝大多数单点劫持。

### 矛盾 3："题库在包里"和"考试保密"冲突

学生端解压后题库就在本地，考试期间只要有人解压成功，题库就泄漏了。真正防泄漏的做法是**在线发题**，但那与"自解压离线包"的需求冲突。折中：

- 题库**按场次分片加密**：包里只放本场次的题（不是全部题库）；
- 每个学生解压后得到的 exe **只能抽自己那份卷**（抽题结果由 `学号+场次` 种子决定），且题库文件在磁盘上是**加密的**，exe 运行时才解密到内存；
- 加"水印"：每份生成的试卷 PDF/界面里嵌入学号水印，泄题可溯源。

## 2. 技术栈选型

### 2.1 管理端

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **Python + PySide6** | 开发最快，JSON/加密生态好，打包 PyInstaller 成熟 | 体积 80–150MB，UI 略土 | ✅ **推荐**（工期紧、以正确性为先） |
| Tauri (Rust + React) | 体积小（~10MB）、UI 现代、与 stub 同语言可共享代码 | 学习曲线，构建链复杂 | 可选（追求质感） |
| Electron | UI 生态最好 | 体积 150MB+，内存高 | ❌ 不必要 |

**推荐组合**：`PySide6 + pydantic + cryptography + PyInstaller`。
理由：管理端是"低频、重配置"的工具，开发效率 > 运行时性能；且 Python 处理 JSON schema 校验、CSV 导入最省事。

### 2.2 学生端（关键）

| 方案 | 体积 | 防逆向 | 跨平台 | 结论 |
|---|---|---|---|---|
| **Rust + windows-rs** | ~3–8MB | 强（无运行时、可混淆、静态链接） | 需分平台编译 | ✅ **推荐** |
| C# + .NET AOT | ~15MB | 中（IL 易反编译，AOT 后好些） | 好 | 可选 |
| Go | ~5MB | 中（符号表丰富，易被 GoReSym 还原） | 好 | 可选 |
| Python + PyInstaller | 80MB+ | 弱（pyc 可还原） | 好 | ❌ |

**推荐**：`Rust`，UI 用 `egui`/`eframe`（单文件、无系统依赖）或 `native-windows-gui`。
抽题用 `rand_chacha`（**可复现**，跨平台/跨版本稳定），加密用 `aes-gcm` + `argon2`，压缩用 `zstd`。

> 为什么强调 `ChaCha8Rng`：`rand` 的 `StdRng` 不保证跨版本一致；`ChaCha8Rng` 是**确定性算法**，同样 seed 在任何机器/任何版本都出同一序列 —— 这是"固定种子出固定试卷"的唯一正确做法。

### 2.3 构建器（管理端调用）

独立 CLI（Rust）：`exam-builder build --manifest manifest.json --out StudentClient.exe`
- 输入：题库 JSON、场次表、密钥、stub 模板
- 输出：SFX 单文件
- 好处：可 CI 化、可复现构建、管理端只是"填表单 + 调 CLI"

### 2.4 时间服务

- 自建：`/api/time` 返回 `{ts, nonce, sig}`（Ed25519 签名），部署在 HTTPS 上
- 兜底：`https://www.baidu.com` 的 `Date` 头、`ntp.aliyun.com`
- 客户端内置公钥，验签失败即降级/拒绝

## 3. 关键机制设计

### 3.1 密钥体系

```
master_secret (32B, 管理端随机生成, 每场次一个)
    │
    ├─ K_payload = HKDF(master_secret, info="payload")     → AES-256-GCM 加密题库包
    ├─ K_stub    = HKDF(master_secret, info="stub")        → 分片混淆写入 stub
    └─ K_manifest= HKDF(master_secret, info="manifest")    → 场次表完整性校验
```

**64 位 hex 字符串** = `master_secret` 的 hex 表示（32 字节 = 64 字符）。管理端展示给管理员保管，同时**分片注入** stub。

分片注入示例（stub 内不出现明文）：

```rust
// 32 个 nibble 各自与 (学号 & 0xF)、场次号做 XOR，再存进 const 数组
// 运行时: nibble[i] = TABLE[i] ^ ((sid >> (i%4*8)) & 0xF) ^ (session * 7)
```

### 3.2 时间门禁流程

```
输入学号
  → 并发请求 3 个时间源（超时 2s）
  → 各自验签 / 取 Date 头，计算与本地时钟偏差
  → 中位数作为 now，若三源分歧 > 5min → 报错退出
  → 读取 manifest 中所有场次 (start, end, 学号集合)
  → 找到 now ∈ [start, end] 且 学号 ∈ 集合 的场次
  → 无匹配 → 明确提示（"未到考试时间" / "你不在这场" / "已结束"）
  → 命中 → 拼装密钥 → 解密 → 校验 manifest 签名 → 启动
```

**注意**：场次表本身也要加密（否则学生能读出别人的学号名单和考试时间）。做法：manifest 用 `K_manifest` 加密，stub 用学号+时间先解密 manifest 再匹配 —— 这里有个"鸡生蛋"：要先知道场次才能匹配学号。

> ⚠️ **更正（第四轮复核，2026-10-22）**：早期版本这里声称"试解密即命中，不暴露名单"，**这个说法是错的**，已从文档撤回。
>
> 实际实现（`container.rs::try_unlock_session`）中，`students` 列表是**明文**序列化进信封内层的，外层 key 是 `HKDF(master, "envelope:{session}")`——任何持有 master 的人都能解开。而 master 就在学生端里（stub 现场拼装），所以**逆向出 master 的学生可以读出全班名单和所有场次时间**。
>
> 更根本地：低熵学号（通常是连号）+ 离线可验证 = 必然可枚举，这是信息论层面的结论，不是实现缺陷。任何"离线验证学号是否在名单里"的方案都无法隐藏名单。
>
> 因此本方案的名单隐私保证应如实降级为"**防随手翻看**"，而非密码学保证。若确实需要名单保密，只能改走"按班级/按学生分包"或"在线签到"，二者都与"离线自解压包"的核心需求冲突。
>
> 详见 [代码审阅报告.md](代码审阅报告.md) §S-1。

### 3.3 抽题算法（可复现）

```rust
let mut rng = ChaCha8Rng::seed_from_u64(
    xxh3_64(&[student_id.to_le_bytes(), session_id.to_le_bytes(), salt].concat())
);
// 分层抽题：每个 json 文件按配置抽 n 题，不重复
for exam in exams {
    let mut pool: Vec<usize> = (0..exam.questions.len()).collect();
    pool.shuffle(&mut rng);          // 稳定：ChaCha8Rng + shuffle 实现固定
    let picked = pool[..exam.pick].to_vec();
    // 可选：按题型分层（单选/多选/判断各抽 n 题）
}
```

**关键**：`slice::shuffle` 的实现在 `rand` 大版本间可能变。要绝对稳定，**自己实现 Fisher-Yates**，只依赖 `ChaCha8Rng::next_u32()`，这样跨版本/跨平台 100% 一致。

### 3.4 防转发（可选但强烈建议）

即使密码每场独立，一个学生解压后仍可把 `exam.exe` + 题库转发。缓解：

1. **绑定机器**：首次运行记录主板/CPU 指纹（`wmic csproduct get uuid`），二次运行校验；换机需管理员签发"迁移码"。
2. **在线心跳**（可选）：考试期间每 60s 向服务端上报 `学号+场次+包指纹`，服务端检测同一学号多机并发 → 告警。
3. **水印**：试卷每页页脚嵌入 `学号+时间戳` 的不可见/浅色水印。

## 5. 数据结构（核心）

### 5.1 题库 JSON（单个考试）

```json
{
  "exam_id": "math-2026-final",
  "title": "高等数学 期末考试",
  "pick": 20,
  "questions": [
    {
      "id": "q001",
      "type": "single",
      "stem": "……",
      "options": ["A……", "B……", "C……", "D……"],
      "answer": "B",
      "score": 2
    }
  ]
}
```

### 5.2 Manifest（构建输入，管理端生成）

```json
{
  "version": 1,
  "salt": "hex",
  "sessions": [
    {
      "session_id": 1,
      "start": "2026-12-20T09:00:00+08:00",
      "end": "2026-12-20T11:00:00+08:00",
      "students": [2021001, 2021002],
      "exams": [{"file": "math.json", "pick": 20}]
    }
  ],
  "time_sources": ["https://time.example.com/api/time"],
  "pubkey": "ed25519-pubkey-hex"
}
```

> `students` 用 `i32` 存（题目说"数值保存、不超过 INT_MAX"）。**注意**：真实学号常超 `INT_MAX`（如 202312345678），若必须 ≤INT_MAX 则用 `u32` 且提示用户；否则改 `u64`。建议**实现用 `u64`，校验时限制 ≤ `i32::MAX`**，两头都满足。

## 6. 实施路线（建议 4 个里程碑）

| 里程碑 | 内容 | 验收 |
|---|---|---|
| **M1 骨架** | 题库 schema + 管理端 CRUD + manifest 生成 | 能导入 3 个 json，配置 2 场次，导出 manifest.json |
| **M2 打包** | builder CLI + AES-GCM 加密 + SFX 拼接 | 产出 exe，输入正确学号+改系统时间模拟 → 能解压 |
| **M3 门禁** | 时间服务 + 多源取时 + 签名令牌 + 名单匹配 | 非考试时间/非名单学号 → 拒绝；正常 → 放行 |
| **M4 抽题** | exam.exe 种子抽题 + 渲染 + 导出 | 同一学号同场次多次运行 → 试卷完全一致 |

**每步都要写测试**：
- 抽题确定性：`seed(2021001, 1)` 跑 1000 次结果哈希一致
- 加密往返：加密→解密→字节相等
- 门禁边界：`end` 前 1 秒放行、后 1 秒拒绝
- 篡改检测：改 manifest 一个字节 → GCM 校验失败

## 7. 容易被忽略的坑

1. **学生端解压目录**：不要解压到当前目录（U 盘只读/权限），用 `%LOCALAPPDATA%\Temp\<uuid>`，退出时删除；若 exam.exe 还在运行，用 `MoveFileEx(..., MOVEFILE_DELAY_UNTIL_REBOOT)` 兜底。
2. **杀软误报**：SFX + 自解压 + 加密载荷 = 典型病毒特征。必须**代码签名**（EV 证书），否则 Windows Defender 会直接删。这是本项目最大的落地风险。
3. **多显示器/缩放**：egui 需处理 DPI；输入框要支持粘贴学号、回车提交。
4. **时钟回拨**：学生把系统时间调回考试时间再运行 —— 因为用网络时间，无效；但要防"考试结束后改时间重跑"，需在首次解锁时记录"已解锁"标记（加密文件），二次运行直接进 exam.exe（避免重复解锁）。
5. **题库抽题不足**：某文件题量 < pick，要在构建期就报错，别到考试时炸。
6. **时区**：全部用 UTC 存储，显示时转本地；`chrono` + `time` crate 注意 `+08:00` 解析。

## 8. 如果只能选一句话

**管理端用 Python+PySide6 快速搭配置界面，学生端用 Rust 写 SFX stub（密码分片混淆 + 多源签名时间 + ChaCha8 确定性抽题），题库用 AES-256-GCM 加密、每场一密，构建器独立成 CLI 保证可复现。**

安全上不要追求"绝对防破解"（做不到），而是把攻击成本抬到"需要逆向 + 伪造证书 + 改机器指纹"三件事同时做到，配合水印与在线心跳做**事后追责**，这才是保密考试系统的正确姿势。

## 1. 必须修正的技术错误

### 1.1 `wmic` 已被微软弃用（影响 §3.4 机器指纹）
Windows 11 24H2 起 WMIC 逐步移除，`wmic csproduct get uuid` 在新机器上直接不存在。
→ 改用 CIM（`(Get-CimInstance Win32_ComputerSystemProduct).UUID`）或注册表 `HKLM\SOFTWARE\Microsoft\Cryptography\MachineGuid`。
→ **但更好的选择是直接砍掉机器绑定**，见 §2.1。

### 1.2 `MoveFileEx(..., DELAY_UNTIL_REBOOT)` 需要管理员权限（影响 §7 清理策略）
学生机房账号通常非管理员，调用会静默失败，临时文件残留。
→ 改为：**看门狗子进程延迟删除**（stub 退出前 spawn 一个 detached 小进程，sleep 30 秒后删目录）+ **下次启动时清理上次残留**。零权限要求。

### 1.3 "逐条试解密隐藏名单"可被枚举爆破（影响 §3.2）
学号是低熵数据（通常 ≤ 10¹⁰ 空间，且往往是连号），攻击者拿到 stub 后可以离线穷举学号空间逐条试解密，**名单照样被还原**。这个机制的隐私保证比前文声称的弱得多。
→ 如实降级：名单隐私只做"防随手翻看"，不做密码学保证。真在意名单隐私，按班级/按学生分发不同的包。
→ 试解密机制本身仍可保留（它同时解决了"鸡生蛋"问题），但密钥派生要加 salt 拉慢爆破：`Argon2id(学号 || 场次 || salt, t=3, m=64MB)`，把每次尝试拉到 ~100ms，全空间爆破从几小时变成几十年。

### 1.4 NTP（UDP 123）在校园网经常被防火墙拦（影响 §3.2 时间源）
→ 时间源优先级调整为：**① 自建签名时间服务（HTTPS）② 多家大站 HTTPS `Date` 头（百度/腾讯/阿里，取中位数）③ NTP 仅作兜底**。HTTPS 走 443，机房能上网就基本能通。

### 1.5 随机数种子写法（次要，影响 §3.3）
`seed_from_u64` 内部走 SplitMix64，虽然 `rand` 承诺稳定，但更显式的做法是：
`blake3(学号 || 场次 || salt) → [u8; 32] → ChaCha8Rng::from_seed()`。完全自己掌控字节流，不依赖库的内部实现细节。

## 3. 一个能大幅简化架构的决策：stub 与 exam.exe 合并

原设计的两段式（stub 解压出 exam.exe 再启动）来自需求字面描述，但它带来四个麻烦：临时目录落盘一个 exe、杀软特征翻倍、清理逻辑复杂、密钥要跨进程传递。

**强烈建议合并为单个 exe**：同一个进程内先弹"学号输入窗"，解锁后直接切换到考试界面。
- 无临时解压 exe（只解密题库 JSON 到内存）
- 密钥全程只在内存，不落盘、不过管道
- 构建产物少一个，CI 更快
- "自解压包"的形式完全保留（exe 内嵌加密 payload，运行时解到内存），只改变"内含一个可执行程序"这一实现细节

若确有理由保留两段式（如 exam.exe 要脱离 stub 复用），则密钥必须经 **stdin 管道**传给子进程——**禁止用命令行参数**（任何用户打开任务管理器/进程列表即可见）。

## 4. 便捷性：工具链收敛

原方案是 2 门语言 × 4 个子项目，收敛为：

```
exam-system/                    # 私有 monorepo
├── Cargo.toml                  # workspace: 统一版本号
├── rust-toolchain.toml         # 钉死 Rust 版本，CI/本地一致
├── crates/
│   ├── common/                 # 加密 / schema / 抽题（黄金测试在这）
│   ├── builder/                # 构建器 CLI

├── worker/                     # Cloudflare Worker 时间服务（TS）
├── schemas/
└── .github/workflows/
    ├── ci.yml                  # PR: fmt + clippy + cargo test + pytest（ubuntu）
```

- 学生端/构建器的 exe **不入 git**，走 GitHub Releases。
- 黄金向量测试（固定 seed → 固定试卷 hash）在 CI 里跑 windows + ubuntu + macOS 三平台，顺带免费验证了跨平台确定性。

## 5. Git / GitHub 工程化

### 5.1 仓库与题库
- **必须是私有仓库**：安全设计文档、测试夹具都在里面。
- **真题库永不入库**。三个选项：
  - (a) 本地 `banks/` 目录 gitignore + 加密 U 盘备份 —— **推荐，最简单**；
  - (b) `git-crypt` 加密入库 —— 可版本化，但团队每人要装 git-crypt 配密钥；
  - (c) 独立私有数据仓库 —— 权限分离最干净，管理成本高。
- 仓库里只放**假题库**（几个 demo JSON），供 CI 和开发调试用。

### 5.2 GitHub 托管 ≠ GitHub 分发
私有仓库的 Release 只有协作者能下载，学生拿不到也不需要。**考试包的分发走 U 盘 / 机房内网 / 教学平台，绝不走 GitHub**。GitHub 只托管：源代码、构建产物（给教师的 builder/admin）、文档。

### 5.3 密钥卫生
- `.gitignore` 必须含：`*.key`、`*.pem`、`secrets/`、`banks/`（真题）、`dist/`、`target/`、`.venv/`、`__pycache__/`、`.env`。
- 免费私有仓库**没有** GitHub secret scanning 的 push protection（那是 Advanced Security 功能）→ 用 **gitleaks** 补：本地 pre-commit hook + CI 里再扫一遍。
- 万一密钥或真题进了历史：立即轮换密钥 + `git filter-repo` 清历史 + force push，别只删文件了事。

### 5.4 CI 成本注意
免费私有仓库每月 2000 分钟 Actions 额度，**Windows runner 按 2 倍计费**（实际只有 1000 分钟）。
→ PR 检查只在 ubuntu 跑 `cargo test + pytest`；Windows 构建只在 `main` 合并和打 tag 时跑；cargo 依赖用 `Swatinem/rust-cache` 缓存。这样每月额度绰绰有余。

### 5.5 协作流程
main 分支保护（PR + CI 绿才能合）+ feature 分支 + tag `v*` 触发 release。Dependabot 开 cargo 和 pip 两个生态，免费。

## 6.1 编译工具链：一个被忽略的便捷性硬约束（第三轮复核新增）

**实测发现**：在 Windows 上编译 Rust 代码，无论 target 是 msvc 还是 gnu，都**必须先有一个可用的链接器**。原因是 cargo 编译 proc-macro / build-script 时，这些宏是"运行在编译主机上的小程序"，必须被链接成 exe 才能执行——哪怕你只跑 `cargo check`、哪怕目标平台是 Linux，这一步都绕不开。

链接器只有三种来源，对本项目（C 盘空间不足）的影响如下：

| 链接器来源 | 体积 | 占用盘 | 结论 |
|---|---|---|---|
| VS Build Tools（C++ 工作负载） | 3–7 GB | 默认 C 盘 | ❌ C 盘不够；可 `--installPath D:\BuildTools` 但下载量大 |
| **MinGW-w64 gcc**（`x86_64-w64-mingw32-gcc`） | 约 200–400 MB | **可放 D 盘** | ✅ **推荐**：一条 winget 命令，gnu target 直接可用 |
| rust-lld（Rust 自带） | 0 | 0 | ⚠️ msvc target 可用（`-C linker=rust-lld`），但 **gnu target 缺 `dlltool`，不完整** |

**给开发者的最短路径**（全程只占 D 盘）：

```powershell
# 1. 装 MinGW-w64（装到 D 盘，约 300MB）
winget install --id MartinStorsjo.LLVM-MinGW -e --location D:\tools\llvm-mingw
#    或：scoop install mingw-winlibs   （scoop 本身也装 D 盘）

# 2. 把 MinGW 的 bin 加入 PATH（含 x86_64-w64-mingw32-gcc 和 dlltool）
$env:Path = "D:\tools\llvm-mingw\bin;$env:Path"

# 3. 编译 gnu target
rustup target add x86_64-pc-windows-gnu
cargo build --workspace --target x86_64-pc-windows-gnu
```

在仓库根放一个 `.cargo/config.toml` 把这个选择固化下来，团队成员开箱即用、CI 也能复用：

```toml
# .cargo/config.toml
[target.x86_64-pc-windows-gnu]
linker = "x86_64-w64-mingw32-gcc"
```

> **注意**：这只是"开发机能编译"的权宜方案。最终发给学生机房前，建议在 C 盘清理出空间后切回 `x86_64-pc-windows-msvc` + VS Build Tools 出**正式版**，因为 MSVC 产出的 exe 在 Windows 上的兼容性、杀毒软件误报率、调试符号支持都最好。开发期 gnu 与发布期 msvc 的**代码完全相同**，只是 target 配置切换。
